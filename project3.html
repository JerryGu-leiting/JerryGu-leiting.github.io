Project 3 · Forward kinematics

FK runtime and a choreographed arm

A C++ runtime that takes a URDF and joint angles and publishes the world pose of every link. A state machine drives a 7-DOF demo arm through a choreography, rendered by a three.js viewer.

Robot

I wrote demo_arm.urdf for this demo: 10 links, 9 joints, 7 DOF. The visuals are boxes, cylinders and spheres only, so the viewer needs no mesh files. All four supported joint types are used.

Choreography

15 states, each a joint-space setpoint for all 7 joints. A state is reached when every joint is within ε = 0.02 (rad or m) of its target; the FSM then takes the on_arrival transition. The last state loops back to home.

Implementation

Forward kinematics

  • URDF parsed and validated in the runtime (pugixml for XML only). Root found as the one link that is no joint's child.
  • Joint transform: T_joint(q) = T_origin · T_motion(q). Rotations are unit quaternions built from RPY and axis-angle. No kinematics or transform library.
  • robot_state_publisher: /joint_states in, one transform per joint on /tf at 10 Hz.
  • robot_world_state_publisher: composes /tf from the root down with /global_pose and publishes each link's 4×4 pose (column-major) on /xform_world.

Motion

  • joint_state_publisher: P servo at 20 Hz, gain 4 s⁻¹, speed capped at each joint's URDF velocity limit, positions clamped to joint limits.
  • finite_state_machine: publishes each state's setpoint on /joint_trajectory, checks arrival against /joint_states at 10 Hz.

Viewer

  • three.js page. A Python bridge subscribes to the runtime over TCP and pushes /xform_world to the browser via Server-Sent Events.
  • Meshes are built from each link's URDF <visual>. Each update is loaded with Matrix4.fromArray, which matches the column-major layout.
  • Poses arrive at ~20 Hz; the viewer interpolates between them for smooth playback.
  • Scene rotated −90° about x to map URDF z-up to three.js y-up. This correction lives in the viewer only.
